2. Project Summary

The TalentPop QA App is the internal web application that powers TalentPop's Quality Assurance, Workforce Management, and Operations workflows. It lets QA team leads evaluate agent tickets against configurable scorecards, run client-specific monitoring forms, manage attendance and shift schedules across remote and internal teams, handle attendance dispute resolution between TLs and the WFA team, run performance reviews, and download reports. It exists to consolidate what used to be a sprawl of Google Sheets, Forms, and ad-hoc tools into one role-aware dashboard so each role (TL, OM, AOM, WFA, QA, Admin, etc.) only sees the features they're allowed to use. The app is the operational hub for daily work across the support delivery org and is classified P0 — outages directly block daily QA, attendance, and scheduling operations.

3. Architecture Overview

Frontend — Single Page Application written in JavaScript (JSX, no TypeScript). React 19 with Vite (rolldown variant) for dev/build, Tailwind CSS v4 + Ant Design v5 for styling, classic Redux + redux-thunk for state, and react-router-dom v7 for routing. Hosted on AWS (static bundle behind CloudFront / served from S3); domain managed via Route 53.

Backend — Separate repo: https://github.com/Talentpop1/qa_ai.git. Built with FastAPI (Python). Exposes REST endpoints under https://api.talentpopapp.com. The frontend integrates via a thin Api wrapper class (src/reduxStore/lib/api.js) using fetch with credentials: "include" so HttpOnly cookies are sent automatically. On 401, the wrapper auto-calls /refresh once and retries the original request before bouncing to /login.

Database — PostgreSQL on AWS RDS. Schema is owned by the backend repo; the frontend has no direct DB access. See Section 7 for inferred schema.

External Services / APIs —

  • Google Forms — embedded iframe for the Client Bonus Request Form
  • AWS S3 — file uploads via POST /workforce/reports/upload (response shape includes s3_url)
  • Hubstaff — schedule data is synced via the backend (/schedules/hubstaff-options, mapping_status, acknowledge-sync)
  • Internal AI grading service — referenced as qa_ai_apis and openai/... route prefixes on the backend

Infrastructure — Pure static frontend deployed manually to AWS. No Docker, no CI/CD config in this repo (see Section 10).

5. Key Features (Current State)

Quality Assurance

  • Evaluate Tickets — QA reviewers grade tickets against AI-suggested rubrics; supports filtering by client, agent, channel, and ticket ID.
  • Forms Management — Build and edit QA scorecards: forms → categories → questions, with archive/duplicate/enable-disable controls.
  • QA Settings — Per-client QA configuration (sampling rates, eligible agents, etc.).

Forms (Coaching & Monitoring)

  • Ticket Monitoring Form — Standard ticket QA form for agents.
  • Performance Coaching Form — Coaching session capture for performance reviews.
  • Other Coaching Types — Free-form coaching entries outside the standard ticket QA flow.
  • Client Specific Forms — Custom monitoring forms per client (uploaded directly via POST /openai/client_specific_forms).
  • Google Form — Embedded Client Bonus Request Form via iframe (canonical docs.google.com/forms/...?embedded=true).

Reports / Downloads

  • Download Ticket OR Performance Report — CSV exports filtered by client / agent / event type.
  • Download Client Specific Report — Client-form CSV exports.
  • QA AI Report — CSV downloads of AI-graded QA evaluations.

Workforce / Attendance

  • Remote Team Management — TLs review and resolve attendance alerts for their remote agents (reason picker, notes, attachments, end-date rules).
  • Internal Team Management — Same flow for internal teams with department-level filters.
  • Remote Team Reporting — Read-only attendance reports for remote teams.
  • Internal Team Reporting — Read-only reports for internal teams.
  • Advance Notice Submission — Agents/TLs flag upcoming absences ahead of time.
  • Schedule Management — Hubstaff-synced schedule view; supports filters across user/client/team-lead/project, deactivation, sync acknowledgement, and unmapped-count surfacing. Now also accessible to WFA users (treated like admin — no role-scoped ID filter).
  • Attendance Automation Infractions — Lists rule-engine-detected attendance infractions; supports live filtering, default-to-Active, edit drawer with reason/notes/attachments, Approve (WFA), Mark Resolved (Admin), and Run Automation trigger button.

WFA-specific Attendance Management

  • WFA Remote Team / Internal Team — Workforce Admin team's view to dispute or resolve TL submissions; supports keeping uploaded attachments across reason changes.
  • WFA Attendance Reporting — Cross-team WFA reporting view.
  • WFA OnTime Reporting — On-time metrics view.

Bugs & Features

  • AI-detected bug/feature reports with two action paths: Mark Resolved (admin-only) and stakeholder Approve / Deny (OM-only).
  • Filters: report type, status (resolved/pending), stakeholder decision (approved/denied/pending/all), submitted-by search.

Performance Review

  • Multi-step coaching flow: pick client → agent → channel → fill coaching form → submit resolutions per metric.

Auth / Layout

  • Cookie-based login with auto-refresh on 401.
  • Role-scoped routing — every route is wrapped in ProtectedRoute that checks ROUTE_ROLES[path] against the current user's role.
  • Two layouts: MainLayout (sidebar + outlet) and FullWidthLayout (no sidebar, used for /evalute-form).

8. Environment Variables

Stored in .env at repo root.

Variable What it does Example value
VITE_API_URL Base URL for the backend API. Used by every Api.* call and by the auth /me, /refresh, /login flows. https://api.talentpopapp.com (prod) · http://localhost:8000 (local)
VITE_ENCRYPTION_KEY Fernet symmetric key for any client-side encryption (used by the fernet package). your_fernet_key_here (placeholder)

Important: all VITE_* vars are inlined into the client bundle at build time — they are not secret post-build. The Fernet key here is shared client-side; treat any encryption it provides as obfuscation, not security. Real secrets must live on the backend (api.talentpopapp.com).

13. Security Notes

Authentication

  • Cookie-based session. Backend issues an HttpOnly cookie on POST /login; the frontend never reads it directly. All requests use credentials: "include" so the browser attaches the cookie automatically.
  • On 401 from any API call, the Api wrapper automatically calls POST /refresh (de-duped via a shared refreshPromise) and retries the original request once. If refresh fails, the user is redirected to /login.
  • AuthProvider calls GET /me on mount and falls back to refresh-then-retry on 401.

Authorization (frontend-only enforcement)

  • ROUTE_ROLES (in src/layout/AppRouters.jsx) maps each route to a list of allowed roles.
  • ProtectedRoute checks the current user's role against the route's allowed roles and redirects to an unauthorized page if they don't match.
  • The backend (FastAPI) must independently enforce authorization on every endpoint. Frontend role gating is for UX only, not security. SecOps should verify role checks exist on every backend route in qa_ai repo.

Secrets Management

  • VITE_API_URL and VITE_ENCRYPTION_KEY come from .env at build time. The .env file in the repo contains placeholders/dev URLs only.
  • All VITE_* env vars are inlined into the client bundle at build time — they are public post-build. Never put a true secret here. The VITE_ENCRYPTION_KEY (Fernet) is a shared client-side key — treat any client-side encryption it does as obfuscation, not security.
  • Real API keys live on the backend.
  • Dev/staging credentials in this doc (moiz@talentpop.co / moiz4321) should be moved to a password vault (1Password, Bitwarden, etc.) and replaced here with a reference like "see TalentPop QA App vault entry". Current password is also weak — rotate to a strong one.

Active Security Findings (action items)

  1. Weak dev/staging password (moiz4321) — rotate to a strong unique password and store in the team password manager.
  2. No CSP on index.html. Add a strict Content-Security-Policy header (or <meta> tag) at minimum allowing only self, the API origin, and Google Forms iframe origin.

CORS

  • Backend (FastAPI) must allow credentials: true and explicit allow-list of https://talentpopapp.com and https://dev.talentpopapp.com (no * with credentials). Verify in the qa_ai repo.

Rate Limiting

  • Not implemented at the frontend. Should be enforced at the backend / API gateway (FastAPI middleware or AWS WAF). Confirm with backend team.

Input Validation

  • Frontend does presence and length validation in some places (e.g. 70-char minimum on coaching notes via NotesInput). The backend must independently validate every payload — never trust the client.
  • File uploads go to POST /workforce/reports/upload (S3-backed). Backend should: (a) enforce auth, (b) enforce file-size and MIME-type limits, (c) generate the S3 key (don't trust client-supplied filenames), (d) ideally scan for malware. Verify in the qa_ai repo.
